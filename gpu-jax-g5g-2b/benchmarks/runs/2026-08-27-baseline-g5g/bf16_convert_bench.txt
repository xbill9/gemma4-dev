# bf16 -> float16 host conversion, measured ON THE G5g (aarch64/Graviton2)
# 2026-08-27, i-021f15b2b45e13793, numpy 2.5.2, ml_dtypes 0.6.0, 64 MiB sample.
#
# docs/bf16-weights-on-turing.md records ndarray.astype(float16) on ml_dtypes
# bfloat16 as unusably slow -- E2B's 4.70 GB PLE table "did not finish in 10
# minutes" (2026-08-24) -- and names a view(uint16) bit-shift as the only
# untried direction. Both halves of that are now false.

machine: aarch64 numpy 2.5.2 ml_dtypes 0.6.0
  direct astype      0.058s    1.15 GB/s  bit-identical=True   -> 4.70 GB table would take    4.1s
  via float32        0.035s    1.91 GB/s  bit-identical=True   -> 4.70 GB table would take    2.5s
  bitshift           0.053s    1.27 GB/s  bit-identical=True   -> 4.70 GB table would take    3.7s

# All three are BIT-IDENTICAL, so this is purely a speed question.
# The blocker was a stale ml_dtypes, not a property of Graviton2, and the
# "untried" bit-shift is not even the fastest of the three.
#
# Cross-check on x86_64 the same day: direct astype 1.3 GB/s, bit-shift 10x
# SLOWER. Same conclusion on both architectures.

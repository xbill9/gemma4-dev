# tpu-vllm-v5e1-embed2 — EmbeddingGemma 2 on one TPU v5e chip

An MCP devops agent that provisions a Cloud TPU v5e-1 (Flex-start Queued Resource), serves
**[`google/embeddinggemma-2`](https://huggingface.co/google/embeddinggemma-2)** through vLLM as an
OpenAI-compatible **embedding** endpoint (`/v1/embeddings`), and runs SRE diagnostics against it.

> **Status 2026-10-07: unprovisioned and unmeasured.** The serving configuration comes from reading upstream
> source, not from a boot. `CLAUDE.md` lists what is known and what only the first boot will settle.

## The model

EmbeddingGemma 2 (released 2026-10-06, Apache 2.0) is a Gemma 4-derived bidirectional encoder. It maps text,
code, images, video and audio into one 768-dimensional space. This rig serves **text only**: the vision
(~170M) and audio (~300M) towers are not loaded, which leaves ~270M parameters. Output is mean-pooled and
L2-normalized. Matryoshka-trained, so the first 512, 256 or 128 values can be kept and renormalized. Context
is 8,192 tokens.

Inputs need the model's task prefixes: `task: search result | query: ` for queries and
`title: none | text: ` for documents. The full table is `EMBED_PROMPTS` in `server.py`.

## Why it needs a patched image

vLLM support for `EmbeddingGemma2Model` merged on 2026-10-06 (vLLM PR #60254). The first `vllm-tpu` image with
it is `nightly-20261007-865ce9b-5ab4e44`, which this rig pins by digest. On TPU the model runs through
tpu_inference's torchax path. Its bidirectional attention kernel was written for BERT-style models and has
two problems with this model:

| Patch | Problem in tpu_inference `865ce9b` | Effect unpatched |
|---|---|---|
| `patches/gqa.diff` | `encoder_only_flash_attention` passes GQA K/V straight to a kernel that requires one K/V head per query head | `ValueError: Head count mismatch` on the first forward |
| `patches/window.diff` | sliding mask is `\|q−k\| <= W`; vLLM's encoder-only convention, and its CUDA backend, is `< W` | each sliding layer sees one extra token per side (a parity error, not a crash) |

The boot script applies them in `patches/ORDER` and serves the result as `vllm-tpu-embed2:patched`.

## Serving command

```
vllm serve google/embeddinggemma-2 --runner pooling --convert embed --max-model-len 8192 \
  --tensor-parallel-size 1 --max_num_batched_tokens 8192 --gpu-memory-utilization 0.80 \
  --limit-mm-per-prompt '{"image":0,"audio":0,"video":0}'
```

`--convert embed` is needed on TPU only: without it the TPU runner advertises no embed task. The batch must
hold a whole request, because bidirectional pooling cannot chunk prefill. All values live in `tpu.env`.

## Quick start

```bash
pip install -r requirements.txt
make mcp-config          # registers the MCP server as tpu-vllm-v5e1-embed2 in .mcp.json
make test && make lint
```

From the MCP client: `find_tpu` or `manage_queued_resource` provisions, `get_system_status` shows progress,
and `verify_model_health` checks dimension, norm and ranking once vLLM answers. `embed_text` and
`rank_documents` exercise the endpoint, and `run_vllm_benchmark` measures it with `vllm bench serve --backend
openai-embeddings`. The full catalog is in [GemmaTools.md](GemmaTools.md), generated by `make tools`.

```bash
curl -s http://<ip>:8000/v1/embeddings -H 'Content-Type: application/json' \
  -d '{"model":"google/embeddinggemma-2","input":["task: search result | query: what is a TPU?"]}'
```

## Not an A/B twin

Every other rig in this monorepo serves a generative checkpoint. Numbers from this rig measure a different
request (no decode) and must never be differenced against theirs.

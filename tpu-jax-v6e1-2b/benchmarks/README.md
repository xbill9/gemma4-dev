# Serving Benchmark Reports

A standard format for capturing what a (model, hardware, engine config) deployment is worth:
identity of the stack, a throughput sweep, capability probes, memory anatomy, startup timeline,
and cost. One JSON file per deployment, validated against `serving-report.schema.json`
(JSON Schema draft 2020-12).

**This file and `serving-report.schema.json` are synced copies.** The originals live in the
monorepo root `benchmarks/`. Edit them there and run `make benchmarks-sync` from the root —
a hand-edit inside a rig is overwritten by the next sync. Everything else under a rig's
`benchmarks/` (its `reports/` and `runs/`) belongs to that rig and is never synced.

## Layout

```
<rig>/benchmarks/
  serving-report.schema.json   synced copy of the canonical schema
  README.md                    synced copy of this file
  INDEX.md                     GENERATED — this rig's reports and runs
  reports/<date>-<model-short>-<hw-short>.json
  runs/<date>-<what>-<hw-short>/
```

`INDEX.md` in each rig and `ROLLUP.md` at the root are both generated by
`benchmarks/rollup.py` (`make benchmarks-rollup`). Don't hand-edit either — a per-rig index
that is maintained by hand drifts into claiming another rig's results, which is exactly what
happened to the run-index table this file used to carry.

## Naming

`reports/<date>-<model-short>-<hw-short>.json`, and **the filename must equal `run.id`**
(e.g. `2026-07-21-gemma4-e2b-v6e1.json`). One file per (model, hardware) cell. Run directories
are `runs/<date>-<what>-<hw-short>/`. Full rules in the monorepo `NAMING.md`.

**`<hw-short>` is the hardware measured, not the rig the file sits in.** Several rigs carry
reports for hardware they are not, because copies travelled with the forks. Never infer a rig's
hardware from a benchmark filename inside it.

## Schema version

Current version is **1.1**. Reports declare their own version in `schema_version`, and both
`1.0` and `1.1` validate — 1.1 is purely additive:

| Added in 1.1 | Why |
|---|---|
| `throughput.sweep[].input_len` / `.output_len` | 1.0 held context length in `workload.input_len`, a single value for the whole sweep, so a two-dimensional (context × concurrency) sweep could not be recorded in one report. A point that sets `input_len` overrides the workload value, making `(input_len, concurrency)` the cell key. |
| `throughput.sweep[].status` (`ok` / `infeasible` / `failed`) and `.error` | 1.0 had no way to say "this cell cannot exist on this chip". An omitted cell is indistinguishable from one never attempted, so a sweep that drops its impossible cells silently overstates its own coverage. |

A non-`ok` cell carries no throughput or latency fields — just its coordinates, status, and
optionally `error`.

## Recording a run

1. Copy an existing report, name it `reports/<date>-<model-short>-<hw-short>.json` (matches `run.id`).
2. Run each sweep point and capture its metrics. Running `vllm bench serve` by hand: pass
   `--save-result`, embed the emitted JSON under `throughput.sweep[].raw`, and copy the headline
   numbers into the typed fields:

   | `vllm bench serve` field | schema path |
   |---|---|
   | `max_concurrency` | `sweep[].concurrency` |
   | `random_input_len` | `sweep[].input_len` (2-D sweeps only) |
   | `request_throughput` | `sweep[].request_rate_rps` |
   | `output_throughput` | `sweep[].output_tok_per_s` |
   | `total_token_throughput` | `sweep[].total_tok_per_s` |
   | `median_ttft_ms` / `p99_ttft_ms` | `sweep[].ttft_ms.median` / `.p99` |
   | `median_tpot_ms` / `p99_tpot_ms` | `sweep[].tpot_ms.median` / `.p99` |
   | `median_itl_ms` | `sweep[].itl_ms.median` |

   `per_stream_tok_per_s` is derived: ≈ 1000 / median TPOT.

   Shortcut where available: the `run_vllm_benchmark` MCP tool with `save_result=True` returns a
   ready-made `throughput.sweep[]` entry. **It is not in every rig** — `tpu-pytorch-inf2-2b` has
   no such tool at all. Check `grep -n "save_result" server.py` before relying on it.
3. Record every cell you decided not to run as `status: "infeasible"` with an `error` line, and
   every cell that failed as `status: "failed"`. Coverage claims in a REPORT.md should quote
   measured / failed / infeasible counts, not just the measured one.
4. Capability probes get a `verdict` per probe (`pass` / `partial` / `fail` / `blocked` /
   `not_tested`) plus a domain-level verdict, with `conditions` recording any config the verdict
   depends on (e.g. `enable_thinking: true`). A model variant that won't load goes in
   `load_matrix`, not `capabilities`.
5. Anything not measured: omit the section. Only `run`, `hardware`, `model`, `software` are required.

## What a run directory should contain

The strongest example in this repo is `runs/2026-07-25-vllm-sweep-v6e1/` (complete in
`tpu-pytorch-v5e1-2b`, `-12b`, and `tpu-pytorch-v6e1-2b`; the copies in `tpu-jax-v5e1-2b`,
`tpu-jax-v6e1-2b` and `tpu-pytorch-inf2-2b` are partial stubs). Its shape is the one to copy:

```
runs/<date>-<what>-<hw-short>/
  REPORT.md            narrative, headline table, coverage counts, practical guidance
  tables.md            full matrices, per model × per metric (ctx \ users)
  results/summary.json machine-readable cells, keyed c<ctx>-u<users>
  results/<model>/     per-cell raw `vllm bench serve` JSON, plus .skip markers
  logs/, *.tgz         per-cell logs
  aggregate.py, *.sh   the scripts that produced it
```

Two properties worth preserving: the **coverage line** in REPORT.md ("252 measured cells, 0
failed, 42 infeasible-by-hardware — recorded, not silently skipped"), and **raw per-cell JSON
kept beside the summary**, so the aggregation can be re-derived rather than trusted.

Set `run.source` in the report to the run directory that produced its numbers, so a report and
its raw data stay connected.

## Validating

```bash
python3 -c "import json,sys; json.load(open(sys.argv[1])); print('JSON OK')" reports/<report>.json
check-jsonschema --schemafile serving-report.schema.json reports/<report>.json
```

`make benchmarks-validate` from the monorepo root validates every report in every rig at once.
If `check-jsonschema` is missing: `pip install check-jsonschema` (no virtualenv — system python3).
The validator falls back to the `jsonschema` Python module if the CLI is absent.

## Why not an existing standard

No public schema covers this combination; the closest are slices of it:

| Standard | Covers | Missing |
|---|---|---|
| `vllm bench serve --save-result` JSON | raw throughput/latency for one run | hardware, cost, capabilities |
| Hugging Face `model-index` (model-card YAML) | eval/capability results, leaderboard-compatible | hardware, serving throughput, cost |
| MLPerf Inference submission format | rigorous perf methodology | capability probes, cost; heavyweight |

This schema embeds the first (see `throughput.sweep[].raw`) and can be exported to the second
if a model card ever needs it.

# CLAUDE.md — gce-pytorch-v6e1-2b

Guidance for Claude Code when working in this repository.

## Project Overview

This repository packages one Claude Code skill (`gce-pytorch-v6e1-2b-management`) and one **Model Context Protocol (MCP) server** (`gce-pytorch-v6e1-2b`, a FastMCP app in `server.py`). Together they:

1. **Operate TPU infrastructure on Compute Engine:** find, provision, and destroy flex-start TPU VMs and run Gemma 4 on them.
2. **Do SRE diagnostics:** verify model health, fetch serving/system/Cloud Logging logs, and triage them (`analyze_cloud_logging`).

**Forked from `tpu-pytorch-v6e1-2b` on 2026-08-29** and migrated onto Compute Engine. Read the two sections below before assuming anything carried over from the parent.

## Slot 1 is `gce`, and that is the whole point of the fork

The parent rig provisions through the **Cloud TPU API** (`gcloud compute tpus queued-resources`). This one provisions through **Compute Engine** (`gcloud compute instances create --machine-type=ct6e-standard-1t --provisioning-model=FLEX_START`). Same silicon, different control plane — see `@NAMING.md` slot 1 for why that earns a slot, and `@HARDWARE.md` for the migration timetable.

The queued-resource tools (`create_tpu_queued_resource`, `manage_queued_resource`, `destroy_queued_resource`, `list_queued_resources`, `describe_queued_resource`, `find_tpu`) **are still registered and still work**, because a project can hold capacity on both planes at once and the parent's field notes are still worth having. They are not this rig's path. The GCE path is `find_tpu_vm` → `create_tpu_vm_instance` → `wait_for_pytorch_ready` → `verify_pytorch_tpu` → `destroy_tpu_vm_instance`.

Endpoint discovery differs by plane and the difference is silent: `discover_vllm_url()` walks ACTIVE queued resources and will return `None` on this rig no matter how healthy the VM is. Use `get_tpu_vm_endpoint(instance_name)`, which resolves the instance's `natIP` directly.

## Slot 2 is `pytorch`, and there are two stacks behind that word

`TPU_BACKEND_INDEX` is the switch, and `_get_pytorch_startup_script` branches on it:

| `TPU_BACKEND_INDEX` | Stack | torch device | Credentials |
| --- | --- | --- | --- |
| unset (**default**) | public `torch` + `torch_xla[tpu]` from PyPI, libtpu from the find-links index | `xla` | none |
| set | the private operator-supplied backend, from an authenticated Artifact Registry | `tpu` | Artifact Registry reader, or the GCS wheel mirror |

**They are mutually exclusive** — installing torch_xla registers the `xla` device, installing the private backend registers `tpu` — so the smoke test and the benchmark harness both read `TORCH_DEVICE` out of `/etc/environment` rather than hardcoding one. Never import the private backend package in code; installing it is what registers the device, and importing it directly is the failure `tests/test_server.py` guards.

The parent rig aborted `workload="pytorch"` outright when the private variables were unset. This one does not: the public path is the default and needs nothing configured. The only remaining abort is `TPU_BACKEND_INDEX` set with an empty `TPU_BACKEND_PIP_SPEC`, which is a half-configured private path.

**Not vLLM.** `workload="vllm"` still exists and still serves through Docker, but a number measured that way is a `vllm` result and does not belong in this rig's `benchmarks/`. File it against a `*-vllm-*` rig.

## Profiling: xprof + tensorboard, all three packages

The boot installs `xprof`, `tensorboard` **and** `tensorboard-plugin-profile`, and all three are load-bearing: xprof is the trace collector `torch_xla.debug.profiler` writes through, tensorboard is the viewer, and the plugin is what teaches the viewer to render an xprof trace. Installing xprof alone leaves you with traces nothing can open. Traces land in `/opt/profiles` on the VM.

`setuptools<81` is pinned in the extras for these three — tensorboard and xprof still import `pkg_resources`, removed in setuptools 81.

## Repository Layout & the Snapshot Sync Model

The repo-root files are authoritative; the skill is distributed as generated copies. **Edit the sources, then run `make skill` — never edit a snapshot directly.**

- **Sources (root):** `server.py` (the MCP server), `project-setup.sh` (installer), `requirements.txt`, `tpu.md` (TPU getting started guide; gitignored, private). The guide's prose is kept vendor-neutral — no Google branding or TPU Builders Program references; only functional `gcloud` commands, API endpoints, and doc/console URLs may contain "google". Preserve that when editing `tpu.md`.
- **Hand-maintained (not regenerated):** `.claude/skills/gce-pytorch-v6e1-2b-management/SKILL.md`, `.claude/skills/gce-pytorch-v6e1-2b-management/mcp/startup_script_template.sh`, `.claude/skills/gce-pytorch-v6e1-2b-management/mcp/startup_script_pytorch_template.sh`
- **Generated by `make skill` (`refresh_skill.py`):**
  - `.claude/skills/gce-pytorch-v6e1-2b-management/mcp/{server.py,project-setup.sh,requirements.txt}` — copies of the root sources
  - `.claude/skills/gce-pytorch-v6e1-2b-management/references/tpu-guide.md` — `tpu.md` with base64 screenshots stripped
  - `skills/gce-pytorch-v6e1-2b-management/` — full copy of the skill in plugin layout (for the marketplace)
- **Generated, gitignored:** `.mcp.json` (embeds the GCP project id) — created by `./init.sh` on first run, or regenerated with `./project-setup.sh . --project <id> [flags]`; never commit it or hand-edit it back into git.
- **Plugin marketplace:** `.claude-plugin/plugin.json` + `.claude-plugin/marketplace.json`. Validate changes with `claude plugin validate .`. The marketplace `/plugin` actually reads is the **monorepo root** copy — keep both in sync.
- **Distribution zip:** `dist/gce-pytorch-v6e1-2b-management-skill.zip`, built by `make skill-package`; committed so the raw-GitHub-URL install works — rebuild it when the skill changes

## Benchmarking

`benchmarks/harness/bench_gemma_torchxla.py` is this rig's harness: greedy decode through transformers on `torch_xla`, one static batch dimension, one run per point after a warmup that is reported as compile time rather than folded into the measurement.

**Its numbers are not comparable to a `vllm bench serve` sweep from a sibling rig.** There is no continuous batching and no paged KV here, so its `concurrency` is a static batch width, not a stream count, and its TTFT is a single prefill rather than a queued request's wait. Differencing it against a `*-vllm-*` report measures the serving stack, not the hardware.

The rig inherited the parent's `benchmarks/reports/` and `benchmarks/runs/` at fork time; both were **deleted** rather than left to be counted twice by `benchmarks/rollup.py`. The originals are still in `tpu-pytorch-v6e1-2b`.

## Common Commands

```bash
make skill         # Refresh all skill snapshots + plugin copy from the root sources
make skill-install # Refresh + copy the skill to ~/.claude/skills (all projects)
make skill-package # Refresh + rebuild dist/gce-pytorch-v6e1-2b-management-skill.zip
make init TARGET=/path/to/project ARGS='--project <id>'  # install skill + register MCP server
claude plugin validate .   # check .claude-plugin manifests
```

The server's config comes from env vars: `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_ZONE`, `MODEL_NAME`, `ACCELERATOR_TYPE`, `TENSOR_PARALLEL_SIZE`, and the `TPU_BACKEND_*` family described above (`_PIP_SPEC`, `_INDEX`, `_FIND_LINKS`, `_WHEELS_GCS`, `_PIP_EXTRAS`, `_ENV_EXPORTS`).

Defaults match the directory name: `google/gemma-4-E2B-it`, `v6e-1`, `TENSOR_PARALLEL_SIZE=1`. The parent rig's defaults contradicted its own name (`v6e-8` / `gemma-4-31B-it` / TP=8) — that drift was fixed here, so do not copy defaults back from a sibling.

## Coding Standards

- **No virtualenvs:** use the system `python3`; if dependencies are missing, warn with the `pip install -r requirements.txt` command instead of creating a venv (this is also how `project-setup.sh` behaves). The startup script follows the same rule on the VM: a dedicated `python3.12` interpreter, installed into directly with `--break-system-packages`, never a venv.
- **Dependency portability:** do not assume third-party libraries like `pandas` are installed. Prefer the standard library (`csv`, `json`) for data parsing and aggregation scripts.
- Every subprocess call goes through `run_command(cmd: list[str])`. **Never `shell=True`.**
- `startup_script_*_template.sh` are rendered through `str.format()`. Any stray literal `{`/`}` raises at format time and breaks the deploy — escape as `{{`/`}}`.
